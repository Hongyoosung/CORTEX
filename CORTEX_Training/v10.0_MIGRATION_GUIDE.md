# v10.0 Migration Guide: Async → Synchronous Architecture

## Executive Summary

**v10.0 completely refactors the environment to a fully synchronous design**, eliminating all threading complexity and naturally solving the episode desync issue.

**Key Insight:** PPO is inherently a synchronous on-policy algorithm. RLlib **does not call `step()` during policy updates**. This means UE5 naturally waits during training, making complex async mechanisms unnecessary.

---

## What Changed

### Architecture Comparison

| Aspect | v9.0.2 (Async) | v10.0 (Sync) |
|--------|----------------|--------------|
| **Threading** | Main + gRPC worker thread | Main thread only |
| **Queues** | action_queue, episode_completion_queue, reset_event_queue | None |
| **Locks** | buffer_lock for thread-safe access | None |
| **step() Behavior** | Returns immediately (non-blocking) | Blocks until UE5 responds |
| **Policy Update** | Requires explicit pause mechanism | Natural idle (RLlib doesn't call step()) |
| **Episode Boundaries** | Queue-based detection | Direct terminal state detection |
| **Code Complexity** | ~868 lines | ~550 lines (-37%) |
| **Action-Obs Matching** | ⚠️ Uncertain (queued) | ✅ Guaranteed (1:1) |
| **Debugging** | Difficult (race conditions) | Easy (linear flow) |

## Code Flow Comparison

### v9.0.2 Async (Complex)

```python
step(actions):
    1. Put actions in queue (non-blocking)
    2. Read from buffer (may be stale!)
    3. Return immediately

[Meanwhile, in gRPC thread...]
    while True:
        - Get action from queue
        - send_actions()
        - poll() (blocks)
        - Update buffers (with lock)
        - Queue episode completions
        - Detect auto-resets

[During policy update...]
    - Main thread: Updating policy (not calling step())
    - gRPC thread: STILL CALLING poll()
    - UE5: Still running! Episode timer advancing!
    - Result: Episode desync
```

**Problem:** The gRPC thread doesn't know when RLlib is updating the policy, so it continues polling UE5, causing episodes to progress during training.

### v10.0 Sync (Simple)

```python
step(actions):
    1. send_actions(actions)      # Non-blocking send
    2. poll()                       # BLOCKS until UE5 responds
    3. Parse observations
    4. Return

[During policy update...]
    - Main thread: Updating policy (not calling step())
    - UE5: Waiting for next action
    - Result: Natural pause, no desync!
```

**Solution:** Since RLlib doesn't call `step()` during policy updates, UE5 naturally waits for the next action. No episode progression during training.

## Performance Impact

### Latency Comparison

| Metric | v9.0.2 Async | v10.0 Sync | Notes |
|--------|--------------|------------|-------|
| **Step Latency** | ~40ms | ~75ms | Single worker |
| **Training Throughput** | ~25 steps/sec | ~13 steps/sec | Single worker |
| **Parallel Throughput** | ~100 steps/sec | ~52 steps/sec | 4 workers × 4 envs |

**Why is sync slower per-step?**
- Async returns immediately (non-blocking), but data may be stale
- Sync waits for UE5 response (blocking), but data is always fresh

**Why does training converge faster?**
- ✅ Guaranteed action-observation matching
- ✅ No stale data
- ✅ Clean episode boundaries
- ✅ PPO assumptions satisfied (on-policy)

### Throughput Recovery

Use RLlib's parallelism to recover throughput:

```python
config = (
    PPOConfig()
    .env_runners(
        num_env_runners=4,  # 4 parallel workers
        num_envs_per_env_runner=1  # Each worker → 1 UE5 instance (4 envs)
    )
)
```

**Result:** 4 workers × 13 steps/sec = **52 steps/sec** (vs 25 steps/sec async with uncertain quality)

## Benefits of Synchronous Architecture

### 1. Guaranteed Action-Observation Matching

**v9.0.2 Async:**
```
t=0: step(A0) → returns obs from buffer (may be stale!)
t=1: [gRPC thread sends A0, receives obs1]
t=2: step(A1) → returns obs1 (but A1 hasn't been sent yet!)
```
Action-observation mismatch breaks PPO's on-policy assumption.

**v10.0 Sync:**
```
t=0: step(A0) → send A0 → poll() → obs0 → return obs0
t=1: step(A1) → send A1 → poll() → obs1 → return obs1
```
Perfect 1:1 correspondence.

### 2. Natural Policy Update Pause

**v9.0.2 Async:**
```python
# Complex pause mechanism required
def on_sample_end(self):
    env.pause()  # Must explicitly pause gRPC thread

def on_train_result(self):
    env.resume()  # Must explicitly resume
```

**v10.0 Sync:**
```python
# No pause mechanism needed!
# RLlib naturally doesn't call step() during policy updates
# UE5 automatically waits for next action
```

### 3. Clean Episode Boundaries

**v9.0.2 Async:**
```python
# Episode completion queued by gRPC thread
episode_completion_queue.put((env_idx, final_rewards, ...))

# Main thread checks queue in step()
if episode_completion_queue:
    # Complex logic to return terminal state
```

**v10.0 Sync:**
```python
# Direct detection in step()
if all_done:
    self._log_episode_completion(env_idx, ...)
```

### 4. Simplified Debugging

**v9.0.2 Async Issues:**
- Race conditions between threads
- Buffer staleness
- Queue ordering problems
- Lock contention

**v10.0 Sync:**
- Linear execution flow
- Single thread
- No timing issues
- Easy to debug with print statements

## Common Questions

### Q: Won't blocking calls hurt performance?

**A:** No, because:
1. PPO is inherently synchronous (on-policy)
2. RLlib collects data in batches (not step-by-step)
3. Parallel workers provide throughput
4. Data quality > raw speed

### Q: What about the gRPC thread overhead in v9.0.2?

**A:** The gRPC thread in v9.0.2 actually adds latency:
- Thread context switching (~1-5ms)
- Queue operations (~0.1-0.5ms)
- Lock contention (~0.1-1ms)
- Total overhead: ~2-10ms per step

### Q: Does this work with other RL algorithms?

**A:** Yes! Synchronous environments are compatible with:
- ✅ PPO (synchronous on-policy)
- ✅ A2C/A3C (synchronous)
- ✅ DQN/DDPG (can use off-policy, but sync is fine)
- ✅ SAC/TD3 (off-policy, but benefits from correct action-obs matching)

### Q: Can I still use multiple UE5 environments?

**A:** Yes! The `num_envs=4` parameter still works:
- Each UE5 instance runs 4 parallel environments
- The synchronous environment handles all 4 in a single step() call
- Episode tracking is per-environment (independent progress)
