# CORTEX v10.0 Quick Start Guide

## What Is v10.0?

v10.0 is a **complete refactor from asynchronous to synchronous architecture**, eliminating all threading complexity and naturally solving the episode desync issue.

**Core Insight:** PPO is synchronous. RLlib doesn't call `step()` during policy updates. Therefore, UE5 naturally waits during training. Complex async mechanisms were actually **causing** the desync problem, not solving it.

**Before modifying training code**, verify the synchronous environment works:

```bash

cd /path/to/CORTEX_UE5

# 2. Run test script
cd CORTEX_Training
python test_sync_env.py
```

**Expected output:**
```

  - Step latency: 75ms (blocking)
  - Episode duration: 30.0s
  - No background threads (fully synchronous)

Ready for training with train_rllib.py!
```

**If tests fail:**
- Check UE5 is running and listening on port 50051
- Verify Schola plugin is loaded
- Check firewall settings

### Step 2: Update train_rllib.py

**Apply these changes** (see `v10.0_train_rllib_changes.patch` for details):

**Change 1: Import new environment**
```python
# OLD (line ~374)
from sbdapm_env_async import SBDAPMAsyncMultiAgentEnv
return SBDAPMAsyncMultiAgentEnv(**config)

# NEW
from cortex_env import CORTEXSyncMultiAgentEnv
return CORTEXSyncMultiAgentEnv(**config)
```

**Change 2: Remove callbacks**
```python
# OLD (line ~303-309)
from policy_update_pause_callback import PolicyUpdatePauseCallback
from ray.rllib.algorithms.callbacks import make_multi_callbacks

MultiCallbacks = make_multi_callbacks(
    [EpisodeLoggerCallback, PolicyUpdatePauseCallback])
config.callbacks(MultiCallbacks)

# NEW
config.callbacks(EpisodeLoggerCallback)
```

**Change 3: Update env name**
```python
# OLD (line ~280)
env="sbdapm_env_async",

# NEW
env="cortex_env",
```

**Change 4: Simplify env_config**
```python
# OLD (line ~252-260)
config = {
    "host": SBDAPMConfig.HOST,
    "base_port": SBDAPMConfig.PORT,
    "grpc_poll_timeout": 0.01,
    "health_reset_threshold": 30.0,
    "warning_steps_threshold": 3000,
}

# NEW
config = {
    "host": SBDAPMConfig.HOST,
    "base_port": SBDAPMConfig.PORT,
}
```

## Troubleshooting

### Problem: "Connection refused" error

**Solution:**
1. Check UE5 is running: `netstat -an | findstr "50051"`
2. Verify Schola plugin loaded in UE5 output log
3. Try `telnet localhost 50051` to test connectivity

### Problem: Episode duration is wrong (not 30s)

**Solution:**
1. Check UE5 GameMode `MaxEpisodeDuration` setting
2. Verify episode timeout is triggered in UE5 logs
3. Check if force timeout in Python is triggering (warning in logs)

### Problem: Step latency is too fast (<30ms)

**Solution:**
- This suggests non-blocking behavior (async mode still active?)
- Verify you're importing `CORTEXSyncMultiAgentEnv`, not `SBDAPMAsyncMultiAgentEnv`
- Check `test_sync_env.py` output for threading warnings

### Problem: Training shows NaN rewards

**Solution:**
1. Check UE5 reward calculation logs
2. Verify observation values are valid (not NaN/Inf)
3. Review PPO hyperparameters (learning rate, clip_param)
4. Check emergency checkpoint logs for instability warnings

## Architecture Benefits

### 1. Guaranteed Action-Observation Matching

**v9.0.2 (Async):**
```
t=0: step(A0) → returns obs from buffer (may be stale!)
t=1: [gRPC thread sends A0, receives obs1]
t=2: step(A1) → returns obs1 (but A1 hasn't been sent yet!)
```
❌ Action-observation mismatch breaks PPO

**v10.0 (Sync):**
```
t=0: step(A0) → send A0 → poll() → obs0 → return obs0
t=1: step(A1) → send A1 → poll() → obs1 → return obs1
```
✅ Perfect 1:1 correspondence

### 2. Natural Policy Update Pause

**v9.0.2 (Async):**
- Requires explicit pause/resume mechanism
- Complex callback coordination
- UE5 integration needed

**v10.0 (Sync):**
- RLlib naturally doesn't call `step()` during policy updates
- UE5 automatically waits for next action
- No coordination needed!

### 3. Simplified Debugging

**v9.0.2 Issues:**
- Race conditions between threads
- Queue ordering problems
- Lock contention
- Buffer staleness

**v10.0 Benefits:**
- Linear execution flow
- Single thread
- No timing issues
- Easy print debugging
