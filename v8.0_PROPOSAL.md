# CORTEX v8.0 Architecture Proposal: Low-Level Action Space Redesign

**Date:** 2026-01-13
**Version:** 8.0 (Major Architectural Redesign)
**Status:** PROPOSAL - Awaiting Approval
**Estimated Implementation Time:** 2-3 weeks

---

## Executive Summary

v8.0 proposes a fundamental redesign of the action space to address architectural redundancy in v7.0 where both MCTS and RL select similar high-level decisions (Mission Type ≈ Strategy Type). The new design shifts RL from **strategic decision making** to **tactical execution**, creating a clearer hierarchical separation:

**v7.0 (Current):**
```
MCTS (Strategic) → Assigns Missions [Assault, Defend, Support, Retreat]
   ↓
RL (Tactical?) → Selects Strategies [Assault, Defend, Support, Retreat]  ❌ REDUNDANT
   ↓
Rules (Execution) → Executes via EQS + NavMesh
```

**v8.0 (Proposed):**
```
MCTS (Strategic) → Assigns Strategies [Assault, Defend, Support, Retreat]
   ↓
RL (Tactical) → Controls Movement Primitives [Stop/Forward + 8 Directions]  ✅ UNIQUE ROLE
   ↓
Rules (Combat) → Auto-targeting + Auto-firing
```

---

## Problem Statement

### Current v7.0 Limitations

1. **Architectural Redundancy:**
   - Mission types and Strategy types are 90% identical
   - RL has limited agency (usually just follows mission type)
   - Two layers making essentially the same decision

2. **Training Inefficiency:**
   - RL learns high-level decisions that MCTS could handle
   - Strategy selection is simple (4 discrete choices) - underutilizes neural network capacity
   - Little emergent behavior (strategies map directly to positions)

3. **Scalability Issues:**
   - EQS queries become bottleneck at scale (50v50 scenarios)
   - Spatial reasoning handled by EQS, not by RL
   - RL doesn't learn tactical movement patterns

### Example of Redundancy

```cpp
// MCTS assigns mission
Mission.Type = EMissionType::Assault;  // "Go attack Point A"

// RL selects strategy (almost always matches mission)
Strategy = EStrategyType::Assault;     // "I'll attack aggressively"

// Rules execute (deterministic)
Position = ETacticalPosition::ForwardCover;  // Always maps Assault → ForwardCover
```

**Result:** RL adds minimal value beyond the MCTS assignment.

## Proposed v8.0 Architecture

### 1. Hierarchical Separation

#### Layer 1: MCTS (Strategic Decision)
**Responsibility:** Team-level strategy assignment
**Frequency:** Async, every 1.5s
**Output:** Strategy + Target Objective for each agent

```cpp
struct FStrategyAssignment
{
    AActor* Agent;
    EStrategyType Strategy;        // Assault, Defend, Support, Retreat
    AObjectiveActor* TargetObjective;  // Which objective to focus on
    int32 Priority;                // Strategy priority (0-10)
};
```

**Example MCTS Assignments:**
```cpp
// 4v4 scenario: Enemy base at Point A, friendly base at Point B
Agent1 → Strategy: Assault,  Target: EnemyBase (Point A)
Agent2 → Strategy: Assault,  Target: EnemyBase (Point A)
Agent3 → Strategy: Defend,   Target: FriendlyBase (Point B)
Agent4 → Strategy: Support,  Target: Agent1 (assist assault)
```

#### Layer 2: RL (Tactical Execution)
**Responsibility:** Low-level movement control
**Frequency:** 10 Hz (every 6 frames at 60 FPS)
**Input:** Observation (68 features) + Assigned Strategy (embedded)
**Output:** Movement primitive (9 discrete actions)

```cpp
// v8.0 Action Space
enum class EMovementAction : uint8
{
    Stop,         // 0: Stop moving
    North,        // 1: Move forward (0°)
    NorthEast,    // 2: Move forward-right (45°)
    East,         // 3: Move right (90°)
    SouthEast,    // 4: Move back-right (135°)
    South,        // 5: Move backward (180°)
    SouthWest,    // 6: Move back-left (225°)
    West,         // 7: Move left (270°)
    NorthWest     // 8: Move forward-left (315°)
};
```

**Action Space Properties:**
- **Size:** 9 discrete actions (vs 4 in v7.0)
- **Control Frequency:** 10 Hz (vs event-driven in v7.0)
- **Execution:** Direct character movement (vs EQS queries in v7.0)

#### Layer 3: Rules (Combat Execution)
**Responsibility:** Automatic targeting and firing
**Frequency:** Every tick (60 Hz)
**Logic:** Script-based, no learning

```cpp
void AutoTargetAndFire()
{
    // Priority: Closest enemy in LOS
    TArray<AActor*> Enemies = PerceptionComp->GetDetectedEnemies();
    AActor* Target = GetClosestEnemyInLOS(Enemies);

    if (Target)
    {
        AIController->SetFocus(Target);  // Auto-aim
        WeaponComp->Fire();              // Auto-fire if has LOS
    }
}
```

## 2. Strategy-Specific Reward Functions

The key innovation: **Each strategy has a unique reward structure**, guiding the RL agent to learn appropriate movement patterns.

### Assault Strategy Rewards

**Objective:** Advance toward enemy objective, engage enemies aggressively

```python
def calculate_assault_reward(agent_state, objective_state):
    reward = 0.0

    # Progress toward objective
    distance_to_obj = get_distance(agent_state.position, objective_state.position)
    if distance_to_obj < agent_state.last_distance_to_obj:
        reward += 0.1  # Moving closer to objective

    # Engagement bonus
    if agent_state.in_enemy_capture_zone:
        reward += 0.2  # Continuous retention reward (v7.0 volume-based)

    # Combat effectiveness
    if agent_state.dealt_damage:
        reward += 1.0 * agent_state.damage_amount / 10.0

    if agent_state.killed_enemy:
        reward += 15.0  # High kill reward for assault

    # Survival penalty (but lower than other strategies)
    if agent_state.died:
        reward -= 8.0

    # Cover usage bonus (tactical assault, not reckless)
    if agent_state.in_cover and agent_state.has_los_to_enemy:
        reward += 0.05  # Reward tactical movement

    return reward
```

**Expected Learned Behavior:**
- Move aggressively toward objective
- Use cover when available (but prioritize advance)
- Engage enemies actively
- Accept moderate risk for progress

### Defend Strategy Rewards

**Objective:** Hold assigned position, deny enemy access

```python
def calculate_defend_reward(agent_state, objective_state):
    reward = 0.0

    # Position holding
    distance_to_defend_position = get_distance(agent_state.position, objective_state.position)
    if distance_to_defend_position < 500:  # Within 5m of objective
        reward += 0.1  # Continuous retention reward
    else:
        reward -= 0.05  # Penalty for abandoning post

    # Area denial
    if agent_state.in_friendly_capture_zone:
        reward += 0.05  # Defending the zone

    # Threat suppression
    if agent_state.dealt_damage:
        reward += 0.8 * agent_state.damage_amount / 10.0

    if agent_state.killed_enemy and distance_to_defend_position < 1000:
        reward += 10.0  # Kill reward (but lower than assault)

    # Survival is critical
    if agent_state.died:
        reward -= 12.0  # Higher death penalty (failed defense)

    # Cover usage highly rewarded
    if agent_state.in_cover:
        reward += 0.1  # Defensive positioning

    return reward
```

**Expected Learned Behavior:**
- Stay near assigned objective
- Use cover extensively
- Suppress enemies approaching objective
- Minimize risk, maximize survivability

### Support Strategy Rewards

**Objective:** Protect assigned ally, draw enemy fire

```python
def calculate_support_reward(agent_state, ally_state):
    reward = 0.0

    # Proximity to ally
    distance_to_ally = get_distance(agent_state.position, ally_state.position)
    if 200 < distance_to_ally < 800:  # Optimal support range (2-8m)
        reward += 0.15  # Stay close but not too close

    # Ally protection
    if ally_state.took_damage and distance_to_ally < 1000:
        reward -= 0.5  # Failed to protect ally

    if agent_state.took_damage and distance_to_ally < 1000:
        reward += 0.3  # Drew fire away from ally (sacrificial)

    # Ally survives
    if ally_state.health_delta > 0:  # Ally gained effective health advantage
        reward += 0.5

    if ally_state.died:
        reward -= 20.0  # Severe penalty for ally death

    # Combat assists
    if ally_state.killed_enemy and distance_to_ally < 1000:
        reward += 5.0  # Assisted ally's kill

    return reward
```

**Expected Learned Behavior:**
- Maintain close proximity to ally
- Position to draw enemy fire
- Suppress enemies threatening ally
- Sacrifice own safety for ally survival

### Retreat Strategy Rewards

**Objective:** Disengage, survive, regroup at safe location

```python
def calculate_retreat_reward(agent_state, safe_zone_state):
    reward = 0.0

    # Distance from threats
    distance_to_closest_enemy = get_min_distance(agent_state.position, all_enemies)
    if distance_to_closest_enemy > agent_state.last_distance_to_enemies:
        reward += 0.2  # Increasing distance from enemies

    # Approach safe zone
    distance_to_safe_zone = get_distance(agent_state.position, safe_zone_state.position)
    if distance_to_safe_zone < agent_state.last_distance_to_safe_zone:
        reward += 0.15  # Moving toward safety

    # Survival paramount
    if agent_state.died:
        reward -= 15.0  # Highest death penalty (retreat failed)

    # Avoid combat
    if agent_state.dealt_damage:
        reward -= 0.2  # Discourage engagement during retreat

    # Successful retreat
    if agent_state.in_safe_zone:
        reward += 10.0  # Reached safety

    return reward
```

**Expected Learned Behavior:**
- Move away from enemies
- Avoid combat
- Seek cover aggressively
- Reach designated safe zone

## 3. Implementation Details

### Network Architecture

**Input:** 68 + 1 = 69 features
- 68 features: Existing observation (agent state, enemies, cover, allies)
- 1 feature: Assigned strategy (one-hot encoded)

**Network:**
```
[69] → FC(128, ReLU) → FC(128, ReLU) → FC(64, ReLU)
                                           ↓
                                 ┌─────────────────┐
                                 │                 │
                          Policy Head(9)    Critic Head(1)
                          Movement Actions   State Value
```

**Output:**
- Policy: 9 logits (one per movement action)
- Value: Scalar value estimate (for MCTS)

### Movement Execution

```cpp
// STTask_ExecuteMovement_v8.cpp
void FSTTask_ExecuteMovement_v8::ExecuteLowLevelMovement(
    FStateTreeExecutionContext& Context,
    EMovementAction Action,
    float DeltaTime) const
{
    FInstanceDataType& InstanceData = Context.GetInstanceData(*this);
    APawn* Pawn = InstanceData.ControlledPawn;

    if (Action == EMovementAction::Stop)
    {
        InstanceData.AIController->StopMovement();
        return;
    }

    // Calculate world direction
    float Angle = static_cast<int32>(Action) * 45.0f - 45.0f;  // Offset for enum indices
    FRotator WorldRotation = Pawn->GetActorRotation() + FRotator(0, Angle, 0);
    FVector MoveDirection = WorldRotation.Vector();

    // Calculate target position (100cm = 1m step)
    FVector CurrentPos = Pawn->GetActorLocation();
    FVector TargetPos = CurrentPos + (MoveDirection * 100.0f);

    // Project onto NavMesh
    UNavigationSystemV1* NavSys = FNavigationSystem::GetCurrent<UNavigationSystemV1>(GetWorld());
    if (NavSys)
    {
        FNavLocation NavLoc;
        if (NavSys->ProjectPointToNavigation(TargetPos, NavLoc, FVector(200, 200, 200)))
        {
            TargetPos = NavLoc.Location;
        }
    }

    // Issue movement command (short distance, low acceptance radius)
    FAIMoveRequest MoveReq(TargetPos);
    MoveReq.SetAcceptanceRadius(50.0f);   // 0.5m acceptance
    MoveReq.SetUsePathfinding(false);     // Direct movement (not pathfinding)

    InstanceData.AIController->MoveTo(MoveReq);
}
```

### Control Loop

```cpp
// FollowerAgentComponent_v8.cpp
void UFollowerAgentComponent::TickComponent(float DeltaTime, ...)
{
    // v8.0: Fixed 10 Hz control frequency
    TicksSinceLastAction++;
    if (TicksSinceLastAction < 6)  // 60 FPS / 10 Hz = 6 ticks
    {
        return;  // Not time for new action yet
    }

    TicksSinceLastAction = 0;

    // Build observation
    FObservationElement Obs = BuildLocalObservation();

    // Get assigned strategy from MCTS (via TeamLeader)
    EStrategyType AssignedStrategy = GetAssignedStrategy();

    // Query RL policy for movement action
    EMovementAction Action = TacticalPolicy->GetMovementAction(Obs, AssignedStrategy);

    // Execute movement
    ExecuteLowLevelMovement(Action);

    // Combat is handled separately (auto-targeting)
    AutoTargetAndFire();
}
```

## 4. Training Considerations

### Curriculum Learning

Progressive difficulty increase to aid convergence:

**Phase 1: Single Strategy Training (Episodes 0-1000)**
```python
# All agents use same strategy, learn basic movement
# Example: All agents assigned Assault strategy
# Learn: Move toward objective, avoid obstacles
```

**Phase 2: Mixed Strategy Training (Episodes 1000-3000)**
```python
# MCTS explores simple 2-2 splits
# Example: 2 agents Assault, 2 agents Defend
# Learn: Different movement patterns per strategy
```

**Phase 3: Dynamic Strategy Assignment (Episodes 3000+)**
```python
# MCTS freely assigns strategies based on game state
# Example: 3 Assault, 1 Support (dynamic based on health)
# Learn: Adaptive tactics, strategy coordination
```

### Reward Shaping

**Dense Intermediate Rewards:**
```python
# v8.0 requires dense rewards (actions are low-level, sparse mission completion too far away)
reward_per_step = 0.0

# Progress rewards (every step)
reward_per_step += proximity_reward(strategy)  # Strategy-specific
reward_per_step += cover_reward(strategy)      # Strategy-specific
reward_per_step += formation_reward(strategy)  # Team coordination

# Combat rewards (event-based)
reward_per_step += damage_reward(strategy)     # On damage event
reward_per_step += kill_reward(strategy)       # On kill event
reward_per_step += death_penalty(strategy)     # On death event

# Terminal rewards (episode end)
if episode_complete:
    reward_per_step += objective_completion_reward(team_performance)
```

### Exploration Strategy

**Epsilon-Greedy with Strategy-Aware Decay:**
```python
def get_epsilon(episode, strategy):
    # Assault and Support: Explore more (risky strategies)
    if strategy in [EStrategyType.Assault, EStrategyType.Support]:
        base_epsilon = 0.3
        decay_rate = 0.9995
    # Defend and Retreat: Explore less (conservative strategies)
    else:
        base_epsilon = 0.2
        decay_rate = 0.999

    return max(0.05, base_epsilon * (decay_rate ** episode))
```

## 5. Performance Analysis

### Computational Cost

**v7.0 (Current):**
```
Update Frequency: Event-driven (~10 updates/sec per agent)
4 agents × 10 Hz × 2-4ms (batched) = 40 inferences/sec × 2-4ms/4 = 20-40ms/sec
Total: ~20-40ms/sec
```

**v8.0 (Proposed):**
```
Update Frequency: Fixed 10 Hz control
4 agents × 10 Hz × 2-4ms (batched) = 40 inferences/sec × 2-4ms/4 = 20-40ms/sec
Total: ~20-40ms/sec (SAME as v7.0 with proper batching)
```

**Key Insight:** Fixed 10 Hz control has similar cost to event-driven updates if properly batched.

### Memory Impact

**v7.0:**
```
ONNX Model: ~400 KB (4 discrete outputs)
Replay Buffer: ~50 MB (high-level experiences)
Total: ~50 MB
```

**v8.0:**
```
ONNX Model: ~450 KB (9 discrete outputs - only 12% larger)
Replay Buffer: ~80 MB (more frequent low-level experiences)
Total: ~80 MB (+60% increase, acceptable)
```

### Training Time

**Estimated Convergence:**
```
v7.0: Strategy selection converges in ~2000 episodes (simple 4-action space)
v8.0: Movement control converges in ~5000 episodes (complex 9-action space + reward shaping)

Ratio: 2.5× longer training time
```

**Mitigation:**
- Curriculum learning (start with single strategy)
- Transfer learning (pre-train on simple scenarios)
- Parallelized training (multiple environments)

## 7. Risk Assessment

### High Risk

**1. Training Instability**
- **Risk:** Low-level actions + sparse rewards = slow convergence
- **Mitigation:** Dense reward shaping, curriculum learning, pretrained initialization

**2. Inference Performance**
- **Risk:** 10 Hz control × 4 agents = 40 inferences/sec might exceed budget
- **Mitigation:** Batched inference, reduce to 5 Hz if needed, profile extensively

### Medium Risk

**3. Reward Engineering Complexity**
- **Risk:** Strategy-specific rewards require extensive tuning
- **Mitigation:** Start with simple rewards, iteratively refine, A/B testing

**4. Emergent Behavior Quality**
- **Risk:** Learned tactics might be inferior to v7.0 EQS-based movement
- **Mitigation:** Compare metrics (win rate, damage dealt, survival), hybrid approach (RL + EQS fallback)

### Low Risk

**5. Code Complexity**
- **Risk:** Major refactor introduces bugs
- **Mitigation:** Comprehensive unit tests, preserve v7.0 branch, incremental rollout

## 10. Open Questions

### Research Questions

1. **Optimal Control Frequency:**
   - 10 Hz (proposed) vs 5 Hz (lower cost) vs 20 Hz (finer control)
   - Need empirical testing to determine sweet spot

2. **Action Space Granularity:**
   - 9 actions (8 directions + stop) vs 5 actions (4 cardinal + stop) vs 17 actions (16 directions + stop)
   - Trade-off: expressiveness vs learning complexity

3. **Reward Function Stability:**
   - How sensitive is training to reward weight changes?
   - Can we meta-learn reward weights via evolutionary search?

### Design Decisions

4. **Auto-Combat vs Learned Combat:**
   - v8.0 proposes auto-targeting, but should aiming also be learned?
   - Possible v8.5 extension: Add aiming offset to action space

5. **EQS Removal vs Hybrid:**
   - v8.0 removes EQS entirely, but could we use EQS for cover detection + RL for approach?
   - Hybrid might accelerate learning (EQS provides spatial priors)

6. **MCTS Frequency:**
   - Current: 1.5s reassignment interval
   - v8.0: Should MCTS run more frequently (0.5s) since RL is now low-level?

## 11. Conclusion

v8.0 represents a **fundamental architectural improvement** over v7.0 by eliminating redundancy between MCTS and RL layers. The shift from high-level strategy selection to low-level movement control gives RL a unique and valuable role in the system.

**Pros:**
- ✅ Clear hierarchical separation (no overlap between MCTS and RL)
- ✅ Emergent tactical behavior (learned movement patterns)
- ✅ Strategy-specific reward shaping (diverse learned behaviors)

**Cons:**
- ❌ Longer training time (2.5× more episodes to converge)
- ❌ More complex reward engineering (strategy-specific functions)
- ❌ Higher inference frequency (10 Hz vs event-driven)
